# Thread scaling appendix: plan

Plan of 2026-11-02, written before the runs. The goal is a thread-scaling experiment in this repository's benchmarking workflow and a new appendix figure for the paper's Thread Scaling subsection (`app:threads`). Code docstrings and the committed thread-scaling manifests cite this file by its bare name, `THREAD_SCALING_PLAN.md`.

## Background

Earlier lab measurements of thread scaling used pre-ms2 code, default memory placement or default THP settings, so none is used in the paper, where every experiment ran on i4i.metal with THP `always`. One of them, bound to NUMA node 0 at 1 to 24 threads, served as the design template.

## Decisions

1. **Rerun**, with the frozen binaries: ms2 2885ee8 (modes min, psi, phi, dual) and ropebwt3 cfad8475.
2. **Index:** HPRC2 human472, the same index files as Fig 5 (already in S3; nothing to build).
3. **Read types:** short reads (`human_short`) and ONT (`human_ont_modern`, HG002 Q28). PacBio and skin are left out.
4. **Read-set size:** 1 Gbase each, a superset of the Fig 5 60 Mb set following the D13.4 rules (A/C/G/T-only filter, whole reads in sampled order, stop at the last read keeping the total at or below 1,000,000,000). The 60 Mb set must be an exact prefix. The ONT pool (`HG002-Q28-s008-seed20261003`) has 44,459 reads and 1,022,850,476 bases; if filtering leaves less than 1 Gbase, use the whole filtered pool and report its exact size. The short-read pool is far larger than needed.
5. **Work division:** ms2 gets `--block-bytes 2097152` at every thread count (about 480 ONT blocks and about 1,000 short-read blocks). ropebwt3 keeps its default `-K 100m`, as in the Fig 5 HPRC2 cells. Both settings are stated in the appendix.
6. **Threads and placement:** i4i.metal socket 0 only. T in {1, 2, 4, 8, 16, 32}, one thread per physical core, pinned with `numactl --physcpubind=<first T physical cores> --membind=0`; plus T = 64 using both SMT siblings of all 32 cores. No cross-socket runs.
7. **ropebwt3 setting:** `-l1` only (full matching statistics, like-for-like with ms2), `-t T`.
8. **Correctness:**
   - New truth (`truth.u32`, `offsets.u64`) for both 1 Gbase sets, made on Rockfish with ropebwt3 `-l1` on the HPRC2 FMD, D13 style.
   - Prefix check: the first 60 Mb of the new truth equals the Fig 5 truth byte for byte.
   - Run 1 of every cell checked against truth by the existing runner path.
   - Cross-thread check: for each tool, mode and read set, the output sha256 is identical at every T.
9. **Figure:** two panels (short, ONT). x is threads, log2, 1 to 64; y is throughput in Mbases/s, log. One line per configuration (ms2-min, psi, phi, dual, ropebwt3 `-l1`), each with a faint dotted ideal line extrapolated from its T = 1 point. The SMT point at 64 uses a hollow marker beyond a shaded break at 32. Generated by `ms2exp.figures` as `figs/threads.pdf` in the same style and tool colors as the other paper figures, with a supporting table of speedup and efficiency in the appendix.
10. **Pilot:** one exclusive Rockfish bigmem node runs all 10 configuration/read-set pairs on the 60 Mb prefixes at T = 1 and T = 32 with every check on; T = 1 times should land near the Fig 5 numbers. Rockfish has no SMT, so the first AWS job runs one short T = 64 cell before the long ones.

## Defaults (chosen without a separate question)

- D6 protocol unchanged: three runs per cell, page cache dropped before each, median reported, ms2 built-in timers, load time measured separately from query time, interleave K = 32, THP `always`.
- A new manifest, `threads-2885ee8-<hash>`, with its own `results/` folder; the frozen manifests are untouched.
- Runner changes: a per-cell `threads` field replacing the hard-coded `--threads 1` in `ms2exp/run/runner.py`, per-cell CPU binding, and `-t` for ropebwt3.
- 70 cells: 7 thread counts x 5 configurations x 2 read sets.
- Cost estimate: about 9 to 10 i4i.metal hours, about $15 to $20 at spot prices.
- Appendix prose follows the paper conventions (observations in past tense, tool behavior in present tense; "modes", not "layouts").

## Work phases

1. Build the two 1 Gbase read sets on Rockfish; check the prefix property.
2. Generate truth on Rockfish; run the truth prefix check.
3. Runner and manifest changes in ms2-experiments; unit tests for the new fields; register inputs.
4. Rockfish pilot (decision 10).
5. Upload the new read sets and truth to S3; run the AWS sweep.
6. Import results, generate `figs/threads.pdf` and the table, write the `app:threads` text.
